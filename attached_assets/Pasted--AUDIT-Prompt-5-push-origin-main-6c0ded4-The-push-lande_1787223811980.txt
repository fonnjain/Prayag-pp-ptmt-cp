## ❌ `machine-capacity-engine.ts:70` — the UTC change made it worse

```javascript
const date = new Date(year, month - 1, d);   // ← LOCAL-time constructor
if (date.getUTCDay() !== 0) count++;          // ← UTC getter
```

Changing the getter without changing the constructor mixes the two clocks. `new Date(2026, 7, 2)` builds **local** midnight; on an IST server that is `2026-08-01T18:30:00Z`, so `getUTCDay()` reports **Saturday** for Sunday 2 August.

The whole month shifts by one day:

| Local date | Actual day | UTC after IST offset | `getUTCDay()` reports |
|---|---|---|---|
| Aug 1 | Saturday | Jul 31 | Friday |
| **Aug 2** | **Sunday** | Aug 1 | **Saturday → counted as a working day** |
| **Aug 3** | **Monday** | Aug 2 | **Sunday → excluded** |

So on the deployment server the wrong day is excluded every week — Sundays counted, Mondays dropped. Before the change it was consistently local and therefore correct; now it is neither.

**Fix:** use the UTC constructor to match the getter, as every other site does.

```javascript
const date = new Date(Date.UTC(year, month - 1, d));
```

Add a test that asserts a known Sunday is excluded — `2026-08-02` — because the current behaviour passes any test that only counts days without checking *which* days.

## ⚠ "B2 caused no shortfall movement" is true, but not for the reason implied

The result is real, and I can show why: `p90(sorted) = sorted[floor(n × 0.9)]`.

| n | index | element |
|--:|--:|---|
| 7 | 6 | maximum |
| 6 | 5 | maximum |

Both select the **maximum**. Sunday output is the *lowest* value in the window (PTMT Aug 2 = 9,683 against 22k–42k on weekdays), so removing it changes the sample size but not the element p90 selects.

Worked example on the PTMT Aug 1–7 window:

```
with Sunday    n=7  idx=6  → p90 = 42,848
without Sunday n=6  idx=5  → p90 = 42,848
```

So "identical output" is correct here — **but it is an artefact of this window, not a general property.** The moment a Sunday's output lands above the p90 element, or a category has 5 days including a Sunday and drops to 4 (crossing the p90 → mean threshold at `:319`), the numbers will move.

Please record it that way. "B2 has no effect" is the wrong lesson to file; the right one is "B2 has no effect when Sunday output is below the p90 element, which held for the 1–7 August window."

Two consequences worth checking:
- **Any category that had exactly 5 observed days including a Sunday now has 4** and switches from p90 to mean. Did that happen for Cistern (5 days in your A2 table)?
- The comparison used the **stale 7 August** baseline. A fresh run at 19 August covers three Sundays (2, 9, 16) over a longer window, where the threshold crossings are far more likely.
