# Root cause found — the 302 is a one-line bug in the machine app

Excellent investigation. Reporting the 302 rather than working around it is what made this findable, and refusing to claim `months_with_data` from static config when the endpoint didn't answer was the right call.

**The cause is in `artifacts/prayag/auth.py`, and it is three lines.**

---

## The bug

```python
# auth.py:152–157
_EXEMPT_EXACT: frozenset = frozenset({"/login", "/logout", "/health"})
_EXEMPT_PREFIX: tuple = ("/static/",)

def _is_exempt(path: str) -> bool:
    return path in _EXEMPT_EXACT or any(path.startswith(p) for p in _EXEMPT_PREFIX)
```

`app.py:83` registers `app.before_request(auth.gate)` — a **global** gate. `gate()` at `:164–179`:

```python
if app_password() is None:
    return None            # gate inactive
if _is_exempt(request.path):
    return None
if not current_user():
    return redirect(url_for("login"))
```

**`/data-api/` is not in either exemption list.** So the session gate fires before Flask ever reaches the blueprint, and `_require_key` — the API-key check — never runs. That is why all three auth forms produced identical 302s: none of them was consulted.

Note `/health` **is** exempt, which matches your finding that it's the one endpoint documented as needing no auth. The API's own `/data-api/v1/health` is a different path and is also gated.

Two corollaries worth stating:

- **The planning app's key is not necessarily wrong.** It has never been evaluated. The 403/500 history and this 302 are one cause, not two.
- **The gate is active because `PRAYAG_APP_PASSWORD` is set** on the deployment. It is inactive when unset (`:172–173`) — which is why this presumably worked before password protection was added, and broke silently when it was.

## The fix (machine app, not ours)

```python
_EXEMPT_PREFIX: tuple = ("/static/", "/data-api/")
```

The API is not left unprotected by this: every `/data-api/v1` route already carries `@_require_key`, so exempting the prefix from the *session* gate hands authentication to the API-key check that was designed for it. `/data-api/v1/health` stays open by design.

This belongs in `fonnjain/Prayag-Plant-MC-Analysis`, not the planning repo. Worth confirming with whoever owns it that the browser UI should stay session-gated while the API uses keys — that is clearly the intent of the code as written.

## On the roster you recovered

Reading it from `sources.py` was the right fallback, and the detail that matters most:

> **`PTMT` has no `2026-08` daily source. It stops at `2026-07`.**

So even once the 302 is fixed, PTMT machine-level data for August will be empty — not because of auth, but because the month was never wired upstream. `PIPE`, `HDPE` and `GARDEN_WB` do have August configured.

Two more:

- **`CP` has an empty daily file map**, so whatever the mapping decision, CP contributes no machine data today.
- **`MOULDING` has no daily sources either** — which weakens the "MOULDING belongs to PTMT" hypothesis on practical grounds regardless of taxonomy.

Your mapping conclusion is well argued and I'd adopt it: `PIPE` + `CP` for the pipe family on the strength of `plan.py`'s own grouping, `PTMT` direct, `MOULDING` unresolved. Declining to place `CP` under PTMT is right — `CP Fittings` at Bhiwari grouped with `PIPE` in the machine app's planning logic is the source's own view, and it outranks the `CP ACCESSORIES` string I saw in PTMT's order data.

## `figures_gated`

Confirmed unhandled. `d.overall` and `d.by_machine` are read; `d.figures_gated` is not. When the 302 is fixed this becomes live immediately — the planning UI would show machine KPIs the source itself considers unreviewed, with no indication.

Worth fixing **before** the 302, so the flag is honoured the first time real data arrives rather than after someone acts on gated figures.
