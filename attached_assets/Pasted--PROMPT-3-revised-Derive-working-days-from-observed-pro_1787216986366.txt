## 1. The problem

| | Intended | App derives | **Actually worked** | Required/Day error |
|---|--:|--:|--:|--:|
| PTMT | 25 | 26 | **29** | **+11.5%** |
| Plumbing | 25 | 26 | **27** | **+3.8%** |

`requiredPerDay = targetMax ÷ workingDays`. Dividing by 26 when the plant worked 29 makes Required/Day 11.5% too high for PTMT June, and required cumulative, days ahead/behind, catch-up per day and the linearity denominator all inherit it.

`d0a7c9a` fixed the numerator. This fixes the denominator. Note also that **no `plant_configs` row exists for June or August**, so 26 is a silent default indistinguishable from a deliberately configured 26.

## 2. ⚠ Correction to the rule I gave you earlier

The original prompt said `workingDays = count of distinct dates with production > 0`. **That is wrong** — it would let an idle weekday shrink the denominator and thereby *improve* Required/Day, rewarding a lost day.

The correct rule keeps the calendar as the base and adds days actually worked outside it:

```
workingDays = |calendar non-Sundays| + |non-calendar days with production > 0|
```

Checks out against the archived evidence:

| | Calendar non-Sundays | Sundays worked | Total | Observed |
|---|--:|--:|--:|--:|
| PTMT June | 26 | 3 (7, 14, 28) | **29** | 29 ✓ |
| Plumbing June | 26 | 1 (7) | **27** | 27 ✓ |

An idle weekday still counts against the plant — which is correct, and is why "1 weekday with no production — Aug 15 (Sat)" is something to **report**, not to remove from the denominator.

## 3. ⚠ An open month needs a projection, not a running count

For a month in progress, `workingDays` cannot simply be days observed so far — that makes `remaining` always zero and `requiredPerDay` climb as the month goes on.

Split it: **past from actuals, future from calendar.**

```
workingDays(open)   = |elapsedDays| + |calendar non-Sundays after snapshotDate|
workingDays(closed) = |calendar non-Sundays| + |non-calendar days with production|
```

For PTMT August at snapshot Aug 19: 18 elapsed days (16 calendar non-Sundays through the 19th, including the idle Aug 15, plus Sundays 2 and 9) + 10 remaining calendar non-Sundays = **28**. If a further Sunday is worked, it rises then — which is correct, not a bug.

## 4. Reuse what `d0a7c9a` already built

`buildElapsedProductionDays(month, dailyByDate, snapshotDate)` is exported and already returns exactly the set you need. For an open month:

```typescript
const elapsed = elapsedDays.length;
```

No new logic — the function that fixed the drop also gives the correct elapsed count.

**But mind the ordering inside `buildPlantBundle`.** Today `elapsed` is computed at `:205–207`, *before* `dailyByDate` exists (`:221`) and before `elapsedDays` is built. You must reorder:

```
dailyByDate  →  elapsedDays  →  elapsed = elapsedDays.length  →  workingDays  →  buildCalendarModel
```

Getting this wrong produces an `elapsed` that silently lags the day list — the same class of mismatch as the positional slice.

Note `:205–206` already sets `elapsed = workingDays` for a **closed or grace** month. That stays correct and needs no change: once `workingDays` becomes observed, a closed month's elapsed follows automatically.

## 9. A decision needed from the team before you build

When the plant works 29 days against a plan built for 25, is Required/Day `target ÷ 29` — the same monthly target spread over the days actually worked — or do the extra Sundays count as production **above** plan?

This prompt assumes the first, which is arithmetically right for pace measurement. **Confirm with the team before implementing.** It changes what "on target" means in a Sunday-working month, and it must not be picked by default.
