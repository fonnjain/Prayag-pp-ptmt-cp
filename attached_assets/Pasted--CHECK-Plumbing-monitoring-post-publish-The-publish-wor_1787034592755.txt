# CHECK — Plumbing monitoring, post-publish

**The publish worked.** The Velocity error banner is the code from `d075625` rendering in production, so the deployed bundle is current. That confirms production is finally on this session's work.

Three findings.

## 1. Attainment: the KPI cards are silently zero while the table beneath has real data

This is the header-vs-table bug class, now in the UI.

Screenshot 2 shows `TOTAL RELEASED 0`, `PRODUCED TO DATE 0`, `CUM. ATTAINMENT –`. Screenshot 3, the same page scrolled down, shows CPVC Pipe with **Total Released 1,60,486 / Total Actual 35,617 / 22.2 %** and CPVC Fitting **8,44,436 / 2,03,014 / 24.0 %**. Both cannot be right.

The cause is a field-name mismatch. The API's Plumbing branch (`monitoring.ts:12–28`) returns:

```jsonc
{
  "plant":      { "produced": …, "mapped": …, "unmapped": …, "runRatePerDay": … },
  "categories": [ … ],
  "weeks":      [ … ]
}
```

There is **no top-level `totalProduced`, no `totalRelease`, and no `weeklyRows`.** But `plumbing-attainment.tsx:54–55, 99` reads exactly those:

```typescript
const totalRelease = data?.weeklyRows?.reduce(…) ?? data?.totalRelease ?? 0;   // → 0
const totalActual  = data?.totalProduced ?? 0;                                 // → 0
…
<div>{fmtN(data?.totalRelease ?? 0)}</div>                                      // → 0
```

Three unresolved fields, three `?? 0` defaults, three confident zeros. `CUM. ATTAINMENT` shows `–` because `attPct` is null when `totalRelease === 0`. The table works because it reads `data.categories`, which **is** returned — and each category carries `totalRelease` / `totalActual` (`plan.ts:2252`), so the correct totals are already in the payload, just not summed.

**Fix (frontend only, no API change needed):**

```typescript
const totalActual  = data?.plant?.produced ?? cats.reduce((s, c) => s + (c.totalActual  ?? 0), 0);
const totalRelease = cats.reduce((s, c) => s + (c.totalRelease ?? 0), 0);
```

Line 99 must use `totalRelease`, not `data?.totalRelease`.

Then assert it: **KPI card total === sum of the table's Total Released column**. That is the same invariant we spent several rounds enforcing between the export header and its TOTAL row; it belongs on this page too.

Note `plant.produced` is Sheet3's *mapped + unmapped* total, whereas summing `categories` gives mapped only. Decide which the card should show and label it — the payload distinguishes them (`plant.mapped` / `plant.unmapped`), and quietly picking one is how the original inflation bugs started.

**`CATEGORIES 11 with release plan`** is correct as coded — `cats.filter(c => c.totalRelease > 0).length` (`:120`). Plumbing has 12 categories, and the table shows CPVC Solvent with a release of 24,338, so the one excluded is presumably AGRI Solvent (1 item, plan 0). Worth confirming, since "11 of 12" is only reassuring if you know which one is missing and why.

## 2. Velocity: 500, not 502 — and the message body is empty

The banner reads *"API error 500: "* — note the trailing colon with nothing after it, and that `plant-live.ts` returns only **502**, **503** or **504** on that route. A **500** means the request failed *before* reaching those handlers, so no JSON error body was produced. That is a different failure from the 502 in your earlier deployment logs.

Worth checking the api-server logs for an unhandled exception on `/api/plant-live/summary` rather than assuming it is still the upstream. `bc9037a` ("Return 504 for upstream timeouts") is on `main` — if production predates it, the 504 path won't be live yet either.

Either way the error banner is doing its job: this is exactly the information the page used to swallow.

## 3. Warnings: "No issues detected" deserves a second look

`PIPE Plant Warnings` shows 0/0/0. But the plant-live service is erroring, and the corrective flags `NOT_STARTED | NO_DEMONSTRATED_CAPACITY` on three Solvent categories, while Attainment's own table shows CPVC Solvent at **0.0 %** against a 24,338 release.

A green "no issues" panel next to a broken data source is the pattern worth being suspicious of. Confirm whether this page derives from `plant-live` (in which case it should be showing the same error, not zeros) or from a separate plant-plan source that genuinely has nothing to report.
