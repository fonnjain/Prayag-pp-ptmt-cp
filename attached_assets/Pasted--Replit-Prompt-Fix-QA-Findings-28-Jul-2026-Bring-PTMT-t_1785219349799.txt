## P1 — BLOCKER: Ops Dashboard content routes all 404

The Ops Dashboard shell loads at `/ops-dashboard/` but every content page shows "Page not found". The wouter `Router` has no `base="/ops-dashboard"`, so a route `path="/"` never matches the full pathname `/ops-dashboard/`.

**Fix:** set the router base path so the dashboard's internal routes resolve. Verify every nav item (Overview, Orders, Production, Stock/Buffer, Sales, Management Reports) loads real content, not "Page not found".

## P2 — HIGH: PTMT monitoring plan-vs-actual is completely broken

PTMT monitoring returns `targetKg = 0`, `categories = []`, `ragBand = null`, and pushes **all 3,636 PTMT items into needsReviewItems**. Root cause: `loadWeightMap()` returns no weight for any PTMT item code, so no plan target can be computed. The machine-level dashboard renders (it reads Report-5 directly), which **masks** the fact that PTMT has no working plan-vs-actual monitoring at all.

Context: Plumbing monitoring works because we built the kg-from-BOM layer for it. PTMT is kg-based but has **no kg source wired**, so this feature was likely never functional.

**Fix:** give PTMT monitoring a working plan target. Options, in order of preference:
1. If PTMT has a BOM/weight source, wire `loadWeightMap()` to it so PTMT item codes resolve to weights (mirror the Plumbing Combined+NEW merge approach).
2. If PTMT has no weight data, make PTMT monitoring **piece-based** (like Plumbing's piece-based categories) rather than kg-based, so plan-vs-actual, category attainment, and the RAG band compute from pieces.

Either way: `categories` must be non-empty, `targetKg`/`targetPcs` non-zero, RAG band computed, and `needsReviewItems` must not contain every item. Verify against real PTMT plan quantities.

## P3 — HIGH (live-wrong-number): PTMT corrective wdr = 27

`POST /corrective/replan` with `{month, segment:"PTMT", weekClosed:0}` returns `workingDaysRemaining = 27` (full month) instead of the actual days remaining. The Plumbing path already defaults `asOfDate = today`; the PTMT path does not. A planner clicking "Re-plan now" late in the month sees a full-month projection (everything feasible, zero shortfall) instead of the true 3-days-remaining picture — misleading at exactly the moment the tool matters.

This is the **same fix already applied to Plumbing**, just not to the PTMT path.

**Fix:** when neither `asOfDate` nor a closed week is supplied, default `asOfDate = today` for PTMT too, and derive wdr from it (exclude Sundays). Verify a PTMT re-plan on 28 Jul returns wdr ≈ 3, not 27, with realistic shortfalls.
