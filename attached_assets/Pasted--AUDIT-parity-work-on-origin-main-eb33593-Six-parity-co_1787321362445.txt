## ⚠ Three things to check

### 1. `normalizePlantSegment` and `isPlantSegment` hardcode the two segments

```typescript
export function isPlantSegment(value: unknown): value is PlantSegment {
  return value === "PTMT" || value === "Plumbing";      // ← not derived
}

export function normalizePlantSegment(value: unknown, fallback = "PTMT") {
  if (normalized === "ptmt") return "PTMT";
  if (normalized === "plumbing") return "Plumbing";     // ← not derived
  return null;
}
```

Both are string comparisons rather than lookups against `PLANT_SEGMENT_PROFILES`. So adding CP to the registry object would widen the *type* but leave these two functions silently rejecting it — and because they return `null` rather than throwing, a CP request would fall back to PTMT or return nothing, with no error. That is the exact silent-default failure mode this project keeps hitting.

Derive them instead:

```typescript
const BY_LOWER = new Map(PLANT_SEGMENTS.map(s => [s.toLowerCase(), s]));
export const isPlantSegment = (v: unknown): v is PlantSegment =>
  typeof v === "string" && BY_LOWER.has(v.toLowerCase());
export const normalizePlantSegment = (v: unknown, fallback: PlantSegment | null = "PTMT") =>
  v == null || v === "" ? fallback : (BY_LOWER.get(String(v).trim().toLowerCase()) ?? null);
```

Then the registry is genuinely the single source, which is the point of the exercise.

### 2. The profile is thinner than the CP spec needs

Current fields: `key`, `label`, `orderGroup`, `workbookDivision`, `actualsSource`. Missing: `categories`, `bufferMultipliers`, `weeklyBands`, `rosterSize`, `units`.

Those still live in `seed.ts` and `sheets.ts`. Fine for now — the comment says CP isn't a reporting segment until its contracts and parity tests exist, which is the right posture — but **the CP data is ready**, and the profile has to grow to hold it:

```typescript
weeklyBands: "per-category" | "uniform" | "none"    // CP is "none"
bufferMultipliers: Record<string, number>            // CP has 1.0 / 1.5 / 2.0
rosterSize: number                                   // PTMT 3,636 · Plumbing 1,120 · CP ~1,916
```

`weeklyBands` matters most: CP has **no** weekly split, and without that field the engine has no way to express it except by branching on the segment name — which is what this work exists to remove.

### 3. Migration 028 sets `captured_commit_sha` to `NULL`

Understandable — the legacy table never recorded it. But it means the migrated July PTMT row carries no build provenance, and that row's KPIs were captured **2026-08-19**, the day *before* the Sunday fix (`d0a7c9a`).

Two consequences: the row is pre-fix and still needs re-capturing, and after migration nothing marks it as such. `backfilled TRUE` is set, which helps, but the reason string says "Migrated from plant_monitoring_snapshots" rather than "captured pre-Sunday-fix".

**Re-capture that row once the working-days precedence is settled** (`b63c703` — "Prefer observed days for completed plant months" — suggests that has landed, so confirm and then re-capture). Re-capturing before the precedence decision would freeze a 12%-wrong denominator for the second time.
