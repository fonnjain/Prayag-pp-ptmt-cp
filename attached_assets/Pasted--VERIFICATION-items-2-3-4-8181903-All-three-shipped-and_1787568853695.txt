## ✅ Item 3 — both readers covered

The diagnostic payload carries source, upload id, filename, rows read/recognised/skipped, resolved and accepted aliases, **present headers**, and the failure reason.

`present` is the field that turns *"pending is zero"* into *"the file has `Quantity`, we accept `Qty`"* in one line. That is the whole value of this item.

## ⚠ The third `.catch` still swallows — and it is now the last silent path

I asked for a **recommendation**, not a change. It came back as neither.

`corrective-engine.ts:461`:

```typescript
fetchLivePendingOrderTotals().catch(err => {
  logger.warn({ err }, "corrective-engine: fetchLivePendingOrderTotals failed");
  return { exact: new Map(), byCode: new Map(), diagnostics: diagnoseInputRows([], …) };
}),
```

**The diagnostics wiring is a real improvement** — the catch now returns a structured diagnostic naming the source and error rather than bare empty maps, so item 4's verifier check will fire on it. Good.

But the swallow remains, and the position has changed since I first raised it: **items 2 and 3 removed every other silent path in this block.** This is the only one left, so it is now the single place where a failed source read produces a plausible-looking corrective.

The argument for leaving it is that the source parses to zero anyway while item 1 is blocked, so nothing is currently lost. **The argument against is that the moment item 1 lands, this catch turns a fetch failure into `deltaNewOrders = 0 − pendingAtPlan`** — silently reverting the order component to exactly the behaviour we are fixing, with only a log line.

**So it should fail loudly at the same time item 1 lands**, not before and not later. Please record that as a stated decision tied to item 1, rather than leaving it as the one unexplained exception in a block whose comment says failures must be loud.

## 0b — the honest answer, and what it means

Refusing to reconstruct run #20's `pending_current` without a verified 17-August snapshot was right. An estimate here would have anchored a business decision to a number nobody could defend.

But that absence is itself the finding, and it should be stated plainly to the team:

> **There is no 17-August snapshot of the open-order book.** The plan froze its items, its plan-run totals and its provenance — but not the order inputs it was built from. So the question *"what were the outstanding orders when run #20 was created?"* has no answer from stored data.

That has a consequence beyond 0b: if the business says `Pending Order` means open balance, then **run #20 cannot be corrected retrospectively** — only future runs can be right. Worth knowing before the decision is made, because it changes what "fix it" can mean.

And it argues for capturing the order snapshot alongside the plan run, the same way `frozenPlanGrandMax` captures the plan total. That is the same lesson as the June workbook drift and the July golden: a plan whose inputs were not preserved cannot be audited later.
