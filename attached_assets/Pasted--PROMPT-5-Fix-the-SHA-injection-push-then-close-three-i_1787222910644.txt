## 1. ⚠ The injected SHA will not exist on GitHub

Your local healthz reports `commitSha: 2cd582b20b453a6b7424b8fb9221ccc51c0ae108`. That is the **local** commit.

We established last round that pushing through the GitHub API creates a **new commit object** — local `d0546b1` became remote `61d9c14…`, because the API rebuilds the commit with a different tree/parent/timestamp. So the sequence is:

1. build injects local `2cd582b…`
2. push creates remote `<something else>`
3. production reports `2cd582b…`, which resolves to nothing on GitHub

That is worse than `(unknown)`. `(unknown)` at least announces that it doesn't know. A hash that looks authoritative and can't be looked up will send someone hunting for a commit that was never published.

**Fix: the injected SHA must be one that exists on the remote, so the build has to happen after the push.**

```
git push  →  git fetch origin  →  GIT_COMMIT=$(git rev-parse origin/main)  →  build  →  publish
```

Read the value from `origin/main` after fetching, or take it from the GitHub API response to the push. Keep the runtime `git rev-parse HEAD` fallback for dev — that is correct there, since dev runs from a real working tree.

Add a check to the publish path: **the injected SHA must resolve on the remote.** If `git cat-file -t <sha>` fails against `origin`, fail the publish rather than deploying an unverifiable build. This has been an open question in four consecutive rounds; a guard ends it.
