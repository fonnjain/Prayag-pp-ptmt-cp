Introduce immutable plan runs so the issued plan is a fixed baseline, while live data continues to feed the corrective re-plan. Apply to both segments (PTMT and Plumbing).

1) FREEZE THE PLAN ON ISSUE. When a plan is run/issued for a month, persist an immutable plan run record containing: the per-item plan quantities (pieces and kg), every input used (avg-3-month sale, stock, pending order, pending-last-month, applied buffer multiplier per item/category), the weekly release assignment, the source data timestamps, and an issued-at timestamp plus a run ID. Once written, a plan run is never mutated — re-running creates a new version (v1, v2 …), it does not overwrite. Keep all versions with their timestamps.

2) KEEP LIVE SYNC, BUT SEPARATE THE TWO VIEWS. Live auto-sync of orders, sales, pending and production continues unchanged. On the Production Planning page show two clearly labelled states:

"As issued" — the frozen plan run (the version the plant received). This is the default view and the version used for all exports unless the user explicitly picks another.
"If re-run today" — the plan recomputed from current live data.
Show the difference between them (per category, pieces and kg) so drift is visible rather than silent. Never let the "as issued" figures change on their own.

3) THE CORRECTIVE RE-PLAN MEASURES AGAINST THE FROZEN BASELINE. The recompute must compare current reality against the issued plan run, not against a moving target. This makes the variance attribution meaningful: for each category, split the change into

production shortfall — issued plan not yet produced,
new demand — orders that arrived after the issued-at timestamp,
capacity infeasibility — remaining work that exceeds capacity in the days left.
These three must reconcile to the total change. Record which plan-run ID and version each corrective run was measured against, and show it in the UI and exports.

4) FIX THE MIXED-FRESHNESS INPUTS. Currently avg3MoSale is read once at plan-build time and never re-read, while pending orders are live — so a recompute is part-frozen, part-live. Make this explicit and consistent: on a corrective run, re-read all demand inputs live (avg-3-month sale, pending orders, new orders, stock, production to date) so "current situation" genuinely means current. If any input cannot be re-read, surface it rather than silently using a stale value.

5) FIX weekClosed ACTUALS FILTERING. In weekClosed mode, actuals are currently used unfiltered, so production after the selected week boundary is wrongly included. Make weekClosed = N resolve internally to asOfDate = last day of week N and run the identical code path, so the two modes always agree.

6) MONTH-END ROLLOVER. At month end, the issued plan run for that month is retained as the historical record. A new month starts a fresh plan run. Past months' issued plans, their corrective runs, and their actuals must remain viewable for audit.

7) EXPORTS. Every export must state which plan run it came from — run ID, version, issued-at timestamp, and for corrective runs the as-of date and working days remaining — so any file can be traced back to the exact data it was produced from.

Regression assertions to add:

Re-running a plan creates a new version and leaves prior versions byte-identical (assert a stored run's quantities are unchanged after a re-run).
A corrective run references a specific plan-run ID, and its three variance components reconcile to the total change.
weekClosed = 1 and asOfDate = last day of W1 return identical results.
"As issued" figures are stable across repeated reads while live sync is running.

Report: confirm plan runs are immutable and versioned, the two views are visible with their difference, the corrective run cites its baseline version, and all assertions pass.
