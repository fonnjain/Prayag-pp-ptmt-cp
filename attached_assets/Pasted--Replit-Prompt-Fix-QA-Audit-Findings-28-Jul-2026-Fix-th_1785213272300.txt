## CRITICAL 1 — Plumbing monitoring shows produced = 0 for all 12 categories

`/plan/plumbing-monitoring` reports `totalProduced = 1,493,014` but every category's `produced` field is `0`. Mapped production is being counted in `totalMapped` internally but is never written to the per-category rows — only the unmapped bucket (≈320,160) surfaces.

**Fix:** in the monitoring aggregation, write each category's mapped production into its category `produced` field, using the same normalised-code matching (uppercase, strip hyphens/spaces/dots) as the plan engine.

**Verify:**
- Each of the 12 categories shows non-zero `produced` where production exists.
- `Σ(category produced) + unmapped = totalProduced` (reconciles exactly).

## CRITICAL 2 — monitoring/dashboard ignores the segment param

`GET /api/monitoring/dashboard?segment=PLUMBING` returns PTMT data verbatim — identical `outputToDateKg` (149,915.1) and `actualPerDay` (6,814.3) for both segments. The route ignores `segment` entirely.

**Fix:** dispatch by segment — PTMT reads the PTMT ANUJ sheet, Plumbing reads Sheet3. Every field in the response must be segment-scoped.

**Verify:** the two segments return **different**, segment-correct numbers; passing `?segment=PLUMBING` no longer returns PTMT machine output.

## HIGH 3 — workingDaysRemaining = 27 always

`GET /plan/corrective-replan` calls the engine with `weekClosed: 0` and no `asOfDate`, so it returns the full month's working days (27) instead of the days actually remaining.

**Fix:** when neither `asOfDate` nor a closed week is supplied, default `asOfDate` to **today** and derive working-days-remaining from it (exclude Sundays, consistent with the 27-working-day month basis).

**Verify:** as of 28 Jul the endpoint returns ~3 working days remaining, not 27; feasibility figures update accordingly.

---

## HIGH 4 — capacityPerDay = 0 in the corrective response

The engine computes p90 from Sheet3 daily production for feasibility correctly, but the response's `capacityPerDay` is read from the unseeded `category_capacity` table, so it shows 0 next to a sensible `feasible` (e.g. "capacity 0 pcs/day, feasible 927,126" — contradictory).

**Fix:** return the **same p90 value used to compute feasibility** in the `capacityPerDay` field, so capacity and feasible are always consistent.

**Verify:** CPVC Fitting `capacityPerDay` ≈ 34,338 (not 0); every category's `feasible = capacityPerDay × workingDaysRemaining`.

## MEDIUM 5 — /api/plan?segment=PLUMBING returns [] silently when FG upload is missing

The required-FG guard only fires in `/plan/validate`, not in the plan GET itself. A UI that doesn't call validate separately reads an empty array as "no plan" instead of "upload missing".

**Fix:** make the plan GET endpoint return an explicit error (HTTP 4xx, clear message: "FG Stock upload required for Plumbing") when the FG upload is absent, rather than an empty array. Do not fall back to sheet numbers.

**Verify:** with no FG upload, `/api/plan?segment=PLUMBING` returns the error, not `[]`.

## MEDIUM 6 — Stale replan goldens (24 failing checks) — NOT an engine bug

The `validate-replan` endpoint hardcodes `asOfDate = 2026-07-14` (workingDaysRemaining = 15). By 28 Jul, ~14 more days of production have accrued (e.g. CPVC Pipe produced 50,032 vs golden 26,980), so the checks fail against a frozen July-14 snapshot. **The engine is correct.**

**Fix (do NOT change the engine):** make `validate-replan` compute its expected values **dynamically from the same live production the engine reads**, so the check is date-independent (preferred). Alternatively parameterise the as-of date and refresh the goldens. Prefer the dynamic approach.

**Verify:** the replan suite passes because it compares like-for-like against current production, not a July-14 snapshot.
