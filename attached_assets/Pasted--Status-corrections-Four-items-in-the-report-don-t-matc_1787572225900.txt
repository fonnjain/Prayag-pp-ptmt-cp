## 4. §2 — the root cause is found, and the fix is small

This is genuinely useful work:

> Browser login uses the **bcrypt-backed `users`** table. The legacy **`app_users`** table holds **scrypt** hashes and is not used by the active login route.

So the verifier is authenticating against the wrong table — or with credentials that exist only in the legacy one. Not a password problem, which is why two replacements didn't help.

**The fix is to create or reset a verifier account in the table the login route actually uses**, then set `REGRESSION_AUTH_EMAIL` / `REGRESSION_AUTH_PASSWORD` to it. That is a one-account change, not an auth migration, and it should not stay blocked.
