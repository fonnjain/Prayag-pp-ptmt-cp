# QA Plan — Prayag Production Planning & Monitoring

Built against `origin/main` at `8c2e7f5`. Covers three frontends, 125 API endpoints, 28 tables and two segments.

**Design principle:** this system's failures have almost never been crashes. They have been **plausible wrong numbers** — production silently discarded, a plan counted twice, a percentage computed on two different populations, a default standing in for a missing value. Tests that only check "does it load" would have caught none of them.

So every section below asks for a **number checked against an independent source**, not a screen that renders.

---

# Part 0 — Environment (do this first, every time)

Nothing below means anything without it.

| Check | Expected |
|---|---|
| `GET /api/healthz` → `commitSha` | equals `git rev-parse origin/main` |
| `GET /api/healthz` → `dbHostname` | the intended database, stated explicitly |
| Migrations applied | 027, 028, 029 present in `_migrations` |
| Suite header | prints DB host and deployed commit |

**If `commitSha` is `(unknown)` or doesn't match, stop.** Four rounds of this project were spent verifying against builds that were never deployed.

# Part 1 — Data integrity (highest value)

These are the checks that would have caught every real defect found so far.

## 1.1 No loaded row goes uncounted

**The invariant:** `Σ dailyOutputs === Σ dailyByDate` for the month.

For each segment × month, compare the raw actuals total against `producedToDate`. Any gap is production being silently dropped.

| Fixture (committed at `047448e`) | Rows | Total |
|---|--:|--:|
| PTMT June 2026 | 2,234 | 933,653 |
| Plumbing June 2026 | 820 | 1,463,741 |
| PTMT August 2026 | 1,058 | 573,456 |
| Plumbing August 2026 | 440 | 696,179 |

**Use the committed CSVs, not live Sheets.** Deterministic, and immune to the quota failures that have repeatedly blocked the suite.

## 1.2 Sunday and non-calendar working days

For each segment × month: distinct production dates, worked Sundays with quantities, and non-Sunday dates with zero production.

Known-good reference: **PTMT June worked 3 of 4 Sundays** (7, 14, 28) totalling 13,146 pcs; **Plumbing June worked 1** (7 June, 19,072).

Assert `workingDays = calendar non-Sundays + non-calendar days with production`. PTMT June → **29**, Plumbing June → **27**. An idle weekday must **not** reduce the count.

## 1.3 Every percentage uses one population

The recurring defect. For each ratio, confirm numerator and denominator cover the same set:

| Metric | Numerator | Denominator |
|---|---|---|
| Cumulative attainment | mapped production **only** | mapped release |
| Plan-vs-Actual `achievementPct` | `mappedProduction` | `totalPlan` |
| Linearity | Σ capped daily | required cumulative |
| Corrective feasibility | Cap/Day basis | remaining-days basis |

Assert `mapped + unmapped === totalProduction` and that the unmapped figure is **displayed**, not just computed. Attainment must not improve when unmapped production rises — that is the signature of a mixed basis.

## 1.4 Plan totals are not double-counted

```
TOTAL PLAN ≤ (largest single version's month total) + (new demand added mid-month)
```

PTMT August read **11.9L** against a ~6.2L monthly plan before the daily-rate fix. Re-verify after `126118c` and record before/after.

Per item: a quantity planned in W1 and rescheduled to W3 by a corrective must count **once**.

## 1.5 Header equals table, everywhere

For every export, the headline figure must equal the sum of the rows beneath it:

- Detail "Original Month Total" = Standard Min TOTAL
- Detail "Revised Month Total" = Standard Max TOTAL
- Per-category plan sums = `kpis.totalPlan`
- KPI card totals = the table columns on the same screen
- `Σ(W1..W4) = TOTAL` per row where weekly banding applies

## 1.6 Item rosters

PTMT **3,636** · Plumbing **1,120** (CPVC 40/244/9 · UPVC 52/242/30 · SWR 160/134/3 · AGRI 123/82/1).

Count from row 2 to the first blank row, the way a consumer would. Explanatory notes and KPI rows must sit **after** a blank separator, never inside the item range.

# Part 2 — Segment parity

Every check in Part 1, run for **both** segments, results side by side. Several defects in this project were "fixed for PTMT, not Plumbing" and cost a round each to find.

Specifically confirm both segments have: plant-level monitoring, closed-month freeze, working-days derivation, snapshot provenance, order and sale columns (or a stated reason for absence), and machine-level data (or a stated reason).

**Segment casing.** For every endpoint accepting `segment`, test `PTMT` / `ptmt` / `PLUMBING` / `Plumbing` / `plumbing` / `NOT_A_SEGMENT`. Recognised values must normalise; unrecognised must return **400 with the value named** — never fall back to another segment's data or return an empty list that reads as "nothing exists".

Same for `month`: `2026-08` valid; `2026-8`, `Aug-2026`, `2026-13`, empty → 400, not `[]`.

# Part 3 — Month lifecycle and freeze

| Month | State | Expected |
|---|---|---|
| Future | `future` | no plan rebuilt from current uploads; named "no plan issued" state |
| Current | `open` | live, recomputes |
| Previous, before the 8th | `grace` | targets frozen, actuals still updating |
| Previous, from the 8th | `closed` | served from snapshot, **byte-identical on repeat calls** |
| Older | `closed` | same |

**The test that matters most: call a closed month twice and diff the responses.** Byte-identical or the freeze isn't working. Everything else can regress quietly; that one cannot.

Boundary cases: `2026-07` is `grace` at 2026-08-07T23:59Z and `closed` at 2026-08-08T00:00Z. Year rollover: `2026-12` closed at 2027-01-08.

Snapshot provenance — every row must carry `captured_at`, `captured_commit_sha`, `backfilled`, `plan_status`. **Assert `captured_commit_sha` is not NULL**; the July PTMT row's missing value is exactly how its defect stayed invisible.

# Part 4 — Exports

For each of Standard Excel, Detail Excel, PDF, weekly Excel, and Plan-vs-Actual Excel:

- Item counts match the roster, read row 2 → first blank
- Header totals equal table totals (Part 1.5)
- Category-level values do **not** appear in per-item columns — Cap/Day, Feasible and Shortfall belong on the KPI row
- `% achieved` is **null**, rendered `—`, when plan is 0 — never `0` or `∞`
- Achievement bands: UNDER < 0.80, ON TARGET 0.80–1.10 **inclusive both ends**, OVER > 1.10, compared by integer cross-multiplication
- Filenames carry the right segment prefix — a Plumbing request must never produce `PTMT_…`
- Provenance rows present: run id, run date, baseline plan run with both stored and computed totals
- Excel and PDF for the same run report **the same** month totals

# Part 5 — Error states

Every one of these must be **visible**, never a zero or a blank:

| Condition | Must show |
|---|---|
| Upstream 502/503/504 | named cause, not "0 kg good" |
| Sheets quota / 403 | the actual status, distinguishable from each other |
| No plan for a month | "no finalized plan", not `0` |
| Unmapped production | the **quantity**, not just the item count |
| No demonstrated capacity | the flag, on the category |
| `figures_gated: true` from the machine API | "needs review" — currently unhandled |
| Snapshot missing for a closed month | named state, not silent recompute |

Test by forcing each: revoke a key, request an unconfigured month, point at an empty workbook.

# Part 6 — UI

**Navigation:** landing route is Plant Level → Control Board, not Machine Level; the active sidebar item is highlighted; both PLANT LEVEL and MACHINE LEVEL groups render on every view; the sidebar never renders empty.

**Layout:** the sticky header doesn't overlap content on scroll; no horizontal scrollbar floats over cards; account controls aren't clipped.

**Charts:** legend swatch colours match series colours; Y-axis ticks are evenly spaced with a round maximum — `0 / 45 / 90 / 166.37%` is a defect.

**Tables:** truncated names have tooltips; headers don't wrap awkwardly.

**Filters:** segment, month, category and period each change the data; a closed month shows its state; a future month shows the no-plan state.

---

# Part 7 — Regression and release

**Before every release:**

1. `tsc --noEmit` clean from a **clean checkout of the pushed commit**, not the workspace
2. Every source file parses — no file with 0 imports starting mid-token *(the truncation signature that hit three times)*
3. API unit suite, with the count
4. Live verifier, reported **separately** — a quota failure is not a pass
5. Byte sizes match between local and remote
6. `/healthz commitSha` equals `origin/main` after publishing

**Commit hygiene:** the message lists every file in the diff. A diffstat that doesn't match the description stops the release — that is how a 1,193-line deletion went unnoticed for four commits.

---

# Part 8 — The ten checks that catch the most

If time is short, run only these:

1. `Σ dailyOutputs === Σ dailyByDate` per segment × month
2. Closed month returns **byte-identical** responses on repeated calls
3. Header total equals table total in every export
4. `mapped + unmapped === totalProduction`, unmapped displayed
5. Item counts match roster, read row 2 → first blank
6. Unrecognised segment returns **400**, never another segment's data
7. `TOTAL PLAN ≤ largest version total + new mid-month demand`
8. `captured_commit_sha` non-NULL on every snapshot
9. `/healthz commitSha` matches `origin/main`
10. Every error state shows a named cause, never a zero

Each corresponds to a defect that actually shipped.
