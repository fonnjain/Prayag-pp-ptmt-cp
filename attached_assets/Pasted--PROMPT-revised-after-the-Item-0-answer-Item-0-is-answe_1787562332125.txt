# ⚠ The finding is sharper than "different universes"

The two sources measure **different quantities**, not two views of one book:

| | Source | Field | Measures |
|---|---|---|---|
| Plan baseline | `DATA.xlsx` upload | `Quantity` | **invoice / order quantity** — what was ordered |
| Live corrective | `Pending order → report` | `Bal. Qty` | **open balance** — what remains unfulfilled |

`deltaNewOrders = pendingNow − pendingAtPlan` is only meaningful when both sides are open balance. **No parser fix can make that subtraction valid** while the baseline is an invoice register.

**And one thing I found that widens this beyond the corrective.** `plan.ts:581–586`:

```typescript
const pendingOrderTotals = sumByKey(
  pendingOrderRows,
  ["Old Item Code", "Item Code", "Item No."],
  ["Colour", "Color"],
  ["Balance_Qty", "Balance Qty", "Bal.Qty", "Qty"],    // ← "Qty" is accepted
);
```

`"Qty"` **is** in the plan's accepted alias list. So the plan builder would take a `Qty` column as pending if one were present under that name. Your report says the upload has a `Quantity` field and zero accepted balance aliases — so `Quantity` ≠ `Qty` and it fell through. **The plan's zero is an accident of naming, not a design decision.**

That matters: if the upload's column were named `Qty` instead of `Quantity`, the plan would have silently used 827,733 of invoice quantity as pending orders. The correct outcome was reached for the wrong reason, and the same alias list would produce the wrong outcome on a differently-named file.

# 2 — PTMT actuals must fail loudly ⬤ ship this now

**Unaffected by everything above. No dependencies. Already evidenced.** Two identical dev runs produced different plans because the actuals fetch failed in one.

`corrective-engine.ts:418–425` — Plumbing is deliberately un-caught with a comment saying a missing workbook must fail the replan loudly rather than present as zero. PTMT `.catch`es and returns `[]`.

| Item type | Effect when the fetch fails |
|---|---|
| Planned (`maxProduction > 0`) | `producedToDate → 0`, `remaining = planRev` — **remake everything already produced** |
| Out-of-plan (`maxProduction = 0`) | `planRev → 0` — **item vanishes from the corrective** |

The second is what you observed: `123-FH`, `124-FH`, `1375-SP` all dropped to 0 across identical runs.

**Remove the `.catch`.** No business decision here — the Plumbing comment already states the principle, and it is segment-independent. Add a test asserting a failing actuals fetch **rejects** rather than resolving with `[]`.

# 3 — Say when a needed column is missing ⬤ do this now, it is what made 0b findable

Your Item 0 investigation produced the decisive number: **14,787 rows with codes, 14,787 with colours, 0 with an accepted balance alias.** That is what identified the file as an invoice register.

**The code computed all three and reported none of them.** It returned zero silently. You had to go looking.

Make the parsers say it:

```typescript
// When a required field resolves in no row:
logger.warn({
  source: "pending_orders upload",
  uploadId, rowCount,
  resolved: { code: 14787, colour: 14787, balance: 0 },
  accepted: ["Balance_Qty", "Balance Qty", "Bal.Qty", "Qty"],
  present: [...distinct header names in the file],
}, "no accepted open-balance column found — contributing zero pending");
```

Surface it in the plan-validate response too, so it appears on screen rather than only in logs. A plan built with zero pending because a column was missing should say so on the plan.

**Apply to both readers** — `sumPendingUploads` in `corrective-engine.ts` and `sumByKey` in `plan.ts`.

This is the generalised version of item 3 from the earlier prompt, and it is now the highest-value item after 2, because it is what turns this class of defect from invisible into immediate.
