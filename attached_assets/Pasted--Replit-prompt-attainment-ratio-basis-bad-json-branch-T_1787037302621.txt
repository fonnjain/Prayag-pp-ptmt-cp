## 1. `CUM. ATTAINMENT` divides two different populations — overstated, and it improves as data quality worsens

**File:** `artifacts/production-monitoring/src/pages/plumbing-attainment.tsx:59–61`

```typescript
const totalRelease = cats.reduce((s: number, c: any) => s + (c.totalRelease ?? 0), 0);
const totalActual  = data?.plant?.produced ?? cats.reduce((s: number, c: any) => s + (c.totalActual ?? 0), 0);
const attPct = totalRelease > 0 ? (totalActual / totalRelease) * 100 : null;
```

`totalRelease` sums `categories` — **mapped items only**.
`totalActual` uses `plant.produced`, which `artifacts/api-server/src/routes/monitoring.ts:120–122` defines as:

```typescript
const totalMapped   = [...catActual.values()].reduce(…);
const totalUnmapped = unmappedByWeek.reduce(…);
const totalProduced = totalMapped + totalUnmapped;   // ← this is plant.produced
```

So the numerator includes unmapped production, which by definition has no category and therefore contributed nothing to the denominator. **Attainment is overstated by exactly the unmapped quantity, and the number improves as unmapped codes increase** — the metric moves the wrong way against the data-quality problem it should be exposing.

The comment at `:56` already notices half of this ("mapped items only") but `:60` then reaches for the wider figure.

### Change

```typescript
const totalRelease = cats.reduce((s: number, c: any) => s + (c.totalRelease ?? 0), 0);
// Mapped-only actual — must share a population with totalRelease, which is
// summed from categories. plant.produced is mapped + unmapped (monitoring.ts:122);
// using it here would inflate attainment by the unmapped quantity and make the
// metric improve as unmapped codes increase.
const mappedActual = cats.reduce((s: number, c: any) => s + (c.totalActual ?? 0), 0);
const attPct = totalRelease > 0 ? (mappedActual / totalRelease) * 100 : null;

// Sheet3 total (mapped + unmapped) — correct for the PRODUCED TO DATE card,
// which is labelled "pcs from Sheet3". Not for the ratio.
const totalActual = data?.plant?.produced ?? mappedActual;
```

Keep `totalActual` on the **PRODUCED TO DATE** card (`:111`) — that label is accurate. Use `attPct` from `mappedActual` for **CUM. ATTAINMENT** only.

### Also surface the unmapped figure

The payload already carries `plant.mapped` and `plant.unmapped`. Add `plant.unmapped` as a visible number next to the attainment percentage — an unmapped quantity sitting beside the ratio is precisely the data-quality signal the unmapped-code catches in `HANDOVER §2` were about. Right now it is fetched and discarded.

### Same defect in Recommendations

`artifacts/production-monitoring/src/pages/plumbing-recommendations.tsx:53–55` has the identical construction for `cumPct`. Apply the same change.

### Add two assertions

Both are one-liners and both prevent this class returning silently:

1. **KPI `TOTAL RELEASED` === sum of the table's `Total Released` column.** Same invariant as the export header-vs-TOTAL check.
2. **`mappedActual + plant.unmapped === plant.produced`.** If this ever fails, the payload's own arithmetic has drifted.

Put them wherever the page's other checks live, or in the regression suite if the monitoring payload is covered there.

## 2. `plant-live.ts` — JSON-parse failure is mislabelled as unreachable

**File:** `artifacts/api-server/src/routes/plant-live.ts`, the `/plant-live/summary` catch block.

When the upstream returns **HTML with a 2xx status** — which is what is happening now, per the production logs — `await upstream.json()` throws `SyntaxError`, falls to the catch, and since it is not a `TimeoutError`, returns:

```typescript
res.status(502).set("X-Upstream-Error", "non-2xx").json({
  error: "Failed to reach prayag-plant.com",
  upstreamErrorType: "non-2xx",
});
```

Both statements are wrong in this case: the upstream **was** reached, and it **did** return 2xx. "Unreachable" sends whoever reads it to check networking, when the real cause is almost always an auth page or error page served with status 200.

### Change

Add a third branch, mirroring the timeout split already in place:

```typescript
const isTimeout  = err?.name === "TimeoutError";
const isBadJson  = err instanceof SyntaxError;

if (isTimeout) {
  // existing 504 branch — unchanged
} else if (isBadJson) {
  logger.error({ err, bodyPreview: rawBody?.slice(0, 200) }, "plant-live/summary: upstream returned non-JSON");
  res.status(502).set("X-Upstream-Error", "bad-json").json({
    error: "Upstream returned a 2xx response that is not JSON — usually an auth or error page served with status 200",
    upstreamErrorType: "bad-json",
  });
} else {
  // existing 502 non-2xx branch — unchanged
}
```

To log `bodyPreview` you'll need the raw text. Read once and parse from the string:

```typescript
const rawBody = await upstream.text();
res.json(JSON.parse(rawBody));   // SyntaxError here carries rawBody in scope
```

Apply the same three-way split to the other routes in this file that call `upstream.json()`, so all of them report consistently.
