## What's there

`fonnjain/Prayag-Plant-MC-Analysis` is a **Flask** app (`artifacts/prayag/`) with a read-only JSON API at `/data-api/v1`, self-documented at `api.py:214–220`:

| Endpoint | Purpose |
|---|---|
| `GET /health` | liveness, no auth |
| `GET /plants` | plant roster, locations, months wired |
| `GET /periods` | valid period tokens + **months holding data** |
| `GET /summary` | computed figures for a period |
| `GET /records` | raw row-level data |

`summary` returns `period`, `filters`, `overall`, `by_plant`, and — when a `plant` filter is supplied — **`by_machine`** and `by_segment`, plus `confirmation`, `figures_gated`, `quarantined_rows`, `row_count`.

That is exactly the shape `plumbing-velocity.tsx` consumes. So the planning app's `/api/plant-live/summary` proxy is calling a real, matching contract — not a stub.

## Two things this settles

**Auth is `X-API-Key`, with `Authorization: Bearer` accepted** (`api.py:14–15`, `_require_key` at `:80`). The planning app's `PRAYAG_PLANT_API_KEY` maps to `PRAYAG_API_KEY` on this side. So the 403/500 seen earlier is a **key or sharing problem**, not a missing API.

**`GET /periods` returns `months_with_data`** (`:258–260`). That is the endpoint the Velocity error banner already tells users to call, and it answers the "is 2026-08 present upstream?" question directly. Worth calling once — it may resolve the Velocity blank immediately.

## ⚠ The plant roster does not map cleanly to your two segments

`app.py:5233` — `_PLANT_ORDER = ["PIPE", "MOULDING", "PTMT", "HDPE", "GARDEN", "TANK", …]`, and `app.py:3560` adds `CP` and `Compound`.

So the machine app knows **eight or more plants**, while the planning app has **two segments**:

| Planning segment | Likely plant token(s) |
|---|---|
| PTMT | `PTMT` — and possibly `MOULDING`, since PTMT fittings are moulded |
| Plumbing | `PIPE` — **plus** whatever covers Fitting and Solvent |

`plumbing-velocity.tsx` hardcodes `plant: "PIPE"`, and the page footer now says *"PIPE plant only (fitting/solvent excluded)"*. That is honest, but it means **Plumbing machine-level monitoring covers roughly a third of the segment** — 375 pipe items of 1,120.

`plan.py:276` and `:762` treat `plant in ("PIPE", "CP")` as one family, which suggests `CP` may belong with Plumbing rather than being a separate business. That needs confirming, not guessing — `CP` also appeared as `C P` / `CP ACCESSORIES` in the order/sale GROUP values, where it looked like PTMT chrome-plated.

**This is the real gap.** The integration works; the segment-to-plant mapping is incomplete and undocumented.

## And a gate the planning app doesn't surface

`figures_gated` (`api.py:173–176`) is `true` when a confirmation has `status == "error"` and is not released — meaning the machine app itself would show *"needs review"* rather than headline figures.

The planning app receives that flag and, as far as I can see, ignores it. So the planning UI could display machine KPIs that the source system considers unreviewed. Same class as the silent-zero problems: a signal arriving and not being shown.
