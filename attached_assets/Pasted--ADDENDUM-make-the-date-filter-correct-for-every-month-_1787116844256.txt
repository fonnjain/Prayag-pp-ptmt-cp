# ADDENDUM — make the date filter correct for *every* month, not just July

Short answer to "will it work in future as well": **not as written.** The first prompt fixes closed months. It leaves four gaps that will produce wrong numbers on other selections. Please treat this addendum as part of the same task.

---

## Gap 1 — Future months rebuild today's plan and present it as theirs

`plant-ingestion.ts:119`:

```typescript
if (month >= currentMonthStr()) {
  const planItems = await buildPlanItems(month);   // reads CURRENT uploads
```

The comparison is `>=`, so **September 2026 takes the live-rebuild branch**. `buildPlanItems` reads whatever uploads exist right now — August's — and the page renders them as September's targets. No error, no empty state: a confident plan for a month that has no plan.

And my own helper in the first prompt said *"future month — treat as open"*, which is wrong. Correct behaviour:

```typescript
if (month > cur) return "future";   // no plan yet
```

A FUTURE month must render *"No plan issued for September 2026"* — not a rebuild of the current month's uploads. Change the branch to `month === currentMonthStr()` and give future months their own path.

## Gap 2 — The grace period as I described it conflicts with the existing code

I wrote "GRACE = live". But for a month in grace, `month < currentMonthStr()` is already true, so `fetchMonthlyTargets` takes the **historical** branch (master file ID), not the live one. The two definitions disagree.

The right decomposition is not "the whole month is live or frozen" — it's **per data source**:

| Source | When it stops changing | Why |
|---|---|---|
| **Targets / plan** | at plan-run finalisation | already immutable in `plan_runs` / `plan_run_results` — should never be rebuilt for a past month |
| **Actuals** | at the close cutoff (7th of the following month) | this is what the grace period is *for* — late Sheet entries |
| **Calendar** (`workingDays`, `snapshotDate`) | at month end | fixed by the calendar, not by data arrival |

So GRACE means: **targets frozen, actuals still re-read, calendar already final.** Not "everything live". Please implement it that way — it is both what you actually want and less work than a full live path.

## Gap 3 — Nothing triggers the freeze

The first prompt says "when a month first transitions to CLOSED, persist a snapshot." There is no scheduler in this codebase, so in practice that becomes *"frozen whenever someone first opens the page after the 7th"* — which could be weeks later, against whatever data exists then. Two months could be frozen at very different data vintages with nothing recording it.

Make it explicit, and prefer lazy-with-provenance over a cron you have to maintain:

- On any read of a CLOSED month with no snapshot: build it, persist it, and record `closedAt`, `capturedAt`, `capturedCommitSha`, and `backfilled: true` when `capturedAt` is materially after the cutoff.
- Surface `capturedAt` in the UI header next to the CLOSED badge. A month frozen on the 7th and one frozen six weeks later are not equally trustworthy, and the reader should be able to tell.

## Gap 4 — `workingDays` silently defaults to 27 in six places

```
monitoring.ts:55, :669
plant.ts:49, :130, :284, :320
```

All `row?.workingDays ?? 27`. July shows **25** because a config row exists (27 non-Sundays minus 2 holidays). Any month **without** a config row silently reports 27 — and a defaulted 27 is indistinguishable from a configured 27.

Every downstream metric divides by this: `requiredPerDay = targetMax / workingDays` (`plant-engine.ts:107`), `remaining`, `catchUpPerDay`, `projectedMonthEnd`. A wrong working-day count quietly biases all of them.

Two changes:
1. Derive the fallback instead of hardcoding it — `countWorkingDaysElapsed(month, lastDayOfMonth)` already computes non-Sundays for any month. Use it.
2. Return `workingDaysSource: "configured" | "derived"` in the payload and show it in the UI, so a derived count (holidays not accounted for) is visible rather than assumed.

## Tests to add to the regression suite

Boundary behaviour is the whole feature, so test the boundaries, not the middle:

1. `resolveMonthState("2026-07", 2026-08-06T23:59Z)` → `grace`
2. `resolveMonthState("2026-07", 2026-08-07T00:00Z)` → `closed`
3. `resolveMonthState("2026-08", 2026-08-19)` → `open`
4. `resolveMonthState("2026-09", 2026-08-19)` → `future`
5. `resolveMonthState("2026-12", 2027-01-07)` → `closed` — **year rollover**, and `new Date(Date.UTC(y, m, 7))` with `m = 12` must land on 2027-01-07, not throw or wrap wrong
6. A CLOSED month returns `elapsed === workingDays` and **zero** weeks marked "upcoming"
7. A CLOSED month's response is **byte-identical across two consecutive calls** — that is what "frozen" means, and it is the one assertion that catches an accidental live path sneaking back in
8. A FUTURE month returns the no-plan state and **never** calls `buildPlanItems`

Test 7 is the important one. Everything else can regress quietly; that one cannot.

## Timezone

`currentMonthStr()` (`plant-ingestion.ts:25`) uses **local** `getFullYear()` / `getMonth()`, while `countWorkingDaysElapsed` uses **UTC** (`getUTCDay`). On a server in IST, "the 7th" arrives 5½ hours before it does in UTC, and around midnight on the 1st the two disagree about which month is current. Pick one — UTC throughout is simplest — and state it in the code comment.
