# PROMPT 2 (revised) — Fix the Sunday production drop

**Supersedes the earlier Prompt 2.** The earlier version contained a sketch that would have introduced a worse bug; the correction is in section 3. Read the whole thing before starting.

**One commit, this change only.** Do not touch `workingDays`, `resolveWorkingDays` or `plant_configs` — that is Prompt 3, and mixing them makes both unreviewable.

---

## 1. The bug

`plant-engine.ts:169–177` builds the day list excluding Sundays:

```typescript
function workingDaysInMonth(month: string): string[] {
  …
  if (!isSunday(iso)) days.push(iso);
}
```

`:226–238` reads only those dates out of `dailyByDate` and sums that array into produced-to-date:

```typescript
const elapsedWorkingDays = allWorkingDays.slice(0, elapsed);
const dailyOutputsArr    = elapsedWorkingDays.map((d) => dailyByDate.get(d) ?? 0);
…
let plantProduced = 0;
for (const v of dailyOutputsArr) plantProduced += v;
```

`dailyByDate` is keyed by **every** date in the loaded actuals, Sundays included. So Sunday rows are fetched, parsed, and then discarded.

Measured from the archived evidence at commit `047448e`:

| | Loaded | Counted | **Discarded** |
|---|--:|--:|--:|
| PTMT June | 933,653 | 920,507 | **13,146** |
| PTMT August | 573,456 | 556,303 | **17,153** |
| Plumbing June | 1,463,741 | 1,444,669 | **19,072** |
| Plumbing August | 696,179 | 665,028 | **31,151** |
| | | | **80,522 pcs** |

Eight worked Sundays across four segment-months. PTMT worked 3 of June's 4.

## 2. The principle

**A day with production is a production day.** No row that was loaded may go uncounted. If a legitimate reason to exclude a row ever exists, it must be an explicit, named, counted exclusion — like the out-of-plan banner — never an implicit one.

## 3. ⚠ The correction — do not use a positional slice

The obvious fix is to add worked Sundays to `allWorkingDays`. **On its own that is worse than the bug**, because two consumers slice that list *positionally* against a count computed on a different basis:

- `:226` — `allWorkingDays.slice(0, elapsed)`
- `:140` — `dailyOutputs.slice(0, elapsed)` inside the linearity calculation

`elapsed` comes from `countWorkingDaysElapsed` (`monitoring-calc.ts:16–28`), which counts **non-Sundays only**. Grow the list to 29 entries for PTMT June while `elapsed` stays 26, and `slice(0, 26)` takes the first 26 of 29 — silently dropping **June 28, 29 and 30**:

| | Qty |
|---|--:|
| Jun 28 (Sun) | 856 |
| Jun 29 (Mon) | 42,386 |
| Jun 30 (Tue) | 34,847 |
| **Newly lost** | **78,089** |

That is six times the 13,146 being recovered, lost the same silent way. **Filter by date; never slice by position.**

```typescript
const allDays = [...new Set([
  ...calendarNonSundays(month),
  ...[...dailyByDate.keys()].filter(d => d.startsWith(month) && (dailyByDate.get(d) ?? 0) > 0),
])].sort();

const elapsedDays     = allDays.filter(d => !snapshotDate || d <= snapshotDate);
const dailyOutputsArr = elapsedDays.map(d => dailyByDate.get(d) ?? 0);
```

And in `computeKPIs` at `:140`, **remove** the `.slice(0, elapsed)` — `dailyOutputs` is already scoped to elapsed days by construction, so slicing again re-creates the mismatch.

Leave `calendar.elapsed` and `calendar.workingDays` at their current values. `requiredPerDay` and `requiredCum` are unchanged in this commit.

## 4. The per-category path needs the same fix

`categoryMap` at `:274–308` builds `dailyOutputs: Array(elapsed).fill(0)` and writes by `dayIdx`. It drops Sundays independently of the plant-level path, so fixing only the plant total leaves category KPIs inconsistent with it. Category totals must reconcile to the plant total afterwards.

## 5. The guard — the most important part

```typescript
const monthKeys    = [...dailyByDate.keys()].filter(d => d.startsWith(month));
const loadedTotal  = monthKeys.reduce((s, d) => s + (dailyByDate.get(d) ?? 0), 0);
const countedTotal = dailyOutputsArr.reduce((s, v) => s + v, 0);

if (Math.round(loadedTotal) !== Math.round(countedTotal)) {
  throw new Error(
    `plant-engine: ${Math.round(loadedTotal - countedTotal)} pcs loaded but not counted for ${month} — ` +
    `every actual row must be attributed to a day`
  );
}
```

**Throw, do not warn.** A silently dropped quantity is precisely what produced this bug; a warning in a log nobody reads is not a guard.

Report any out-of-month dates in `dailyByDate` separately rather than swallowing them — if the fetchers are leaking stray rows, that is its own finding.

Add the equivalent assertion for the per-category path: Σ category produced === plant produced.

## 6. Expect a temporary overstatement — do not compensate for it

After this commit alone, produced covers all worked days while `requiredCum` still covers only calendar non-Sundays. PTMT June's attainment will rise by roughly **1.4%** and be briefly wrong in the *opposite* direction. That is expected. Prompt 3 corrects the denominator.

**Report the intermediate figures; do not adjust anything to make them look right.** And do not publish between commits 2 and 3 — the intermediate state is visibly wrong in production.

5. A month with **no** Sunday production behaves exactly as before — no regression on the normal path.
6. The guard throws when a row is artificially excluded.
