# Item 2 — PTMT actuals must fail loudly

## The defect

`corrective-engine.ts:416–425`:

```typescript
// Do NOT swallow Sheet3 failures: a missing/unreadable workbook must fail
// the replan loudly, never present as zero production (stale-plan hazard).
segment === "Plumbing"
  ? fetchPlumbingSheet3Production(month)
  : Promise.resolve([] as PlumbingSheet3Row[]),
segment === "PTMT"
  ? fetchDailyActuals(month).catch(err => {
      logger.warn({ err }, "corrective-engine: fetchDailyActuals failed"); return [] as DailyActualRow[];
    })
  : Promise.resolve([] as DailyActualRow[]),
```

The comment states the rule. **The line directly beneath it breaks the rule for PTMT.**

## Why it matters — both directions, one observed

Already evidenced: two identical dev runs with the same `asOfDate` produced different plans, because the actuals fetch failed in one.

| Item type | Effect when the fetch fails |
|---|---|
| Planned (`maxProduction > 0`) | `producedToDate → 0`, so `remaining = planRev` — **the plant is asked to remake everything it has already produced this month** |
| Out-of-plan (`maxProduction = 0`) | `planRev = max(0, producedToDate) → 0` — **the item disappears from the corrective entirely** |

The second is what you observed: `123-FH / IVORY`, `124-FH / IVORY` and `1375-SP / IVORY` all dropped to 0 across identical runs.

## Fix

Remove the `.catch` so PTMT behaves as Plumbing does:

```typescript
segment === "PTMT"
  ? fetchDailyActuals(month)
  : Promise.resolve([] as DailyActualRow[]),
```

**No business decision here.** The Plumbing comment already states the principle and it is segment-independent — a corrective computed silently against zero production is not a defensible output for either segment.

## Also check the third `.catch` in the same block

`:426–429` swallows `fetchLivePendingOrderTotals()` failures the same way, returning empty maps. Given item 1 is blocked and that source currently parses to zero regardless, **do not change its behaviour in this commit** — but report whether it should follow, so the decision is made deliberately rather than left as an oversight.

## Tests

- A failing actuals fetch **rejects** rather than resolving with `[]`
- Two identical runs with the same `asOfDate` produce identical `planRev` for every item
- Plumbing's existing fail-loud behaviour is unchanged

# Item 3 — Say when a required column is missing

## Why this is the highest-value item after 2

Your Item 0 investigation produced the number that identified the file: **14,787 rows with codes, 14,787 with colours, 0 with an accepted balance alias.**

**The code computed all three and reported none of them.** It returned zero silently, and you had to go looking. Had it said so, A5 would have been found the day the upload changed shape.

## Where

`corrective-engine.ts:288–299` — `sumPendingUploads`:

```typescript
const code   = (["Old Item Code", "Item Code", "Item No."].map(k => row[k]).find(…));
const colour = (["Colour", "Color"].map(k => row[k]).find(…)) ?? "";
const rawQty = (["Balance_Qty", "Balance Qty", "Bal.Qty", "Qty"].map(k => row[k]).find(…));
if (!code) continue;
```

and `plan.ts:581–586` — `sumByKey`, with the same alias lists.

## What to add

Track resolution counts per field, and when a required field resolves in **zero** rows while rows exist, log it with everything needed to diagnose:

```typescript
logger.warn({
  source: "pending_orders upload",
  uploadId,
  rowCount: rows.length,
  resolved: { code: 14787, colour: 14787, balance: 0 },
  accepted: ["Balance_Qty", "Balance Qty", "Bal.Qty", "Qty"],
  present: [...new Set(rows.flatMap(r => Object.keys(r)))],
}, "no accepted open-balance column found — contributing zero pending");
```

`present` is the field that matters most — it is what turns *"pending is zero"* into *"the file has `Quantity`, we accept `Qty`"* in one line.

**Surface it, not just log it.** Add the same information to the plan-validate response so a plan built with zero pending because a column was missing says so on screen. A warning only in logs is a warning nobody reads.

## One thing worth knowing while you implement this

`plan.ts:585` already accepts **`"Qty"`** in its balance alias list. The upload has a field named `Quantity`. So the plan's zero was reached because `Quantity ≠ Qty` — **one letter, not a design decision.**

Had the column been named `Qty`, the plan would have silently taken **827,733** pcs of invoice quantity as pending orders. The right answer was reached by accident, and the same alias list would give the wrong answer on a differently-named file.

**Do not "fix" this by adding `Quantity` to the alias list.** That is the 0b question below and it is not yours to decide. Item 3 is only about making the silence audible.

## Tests

- A row set with no accepted balance column logs the warning and reports zero
- The warning includes `present` headers and the `accepted` list
- A row set with a valid balance column does **not** warn
- Both `sumPendingUploads` and `sumByKey` behave the same way
