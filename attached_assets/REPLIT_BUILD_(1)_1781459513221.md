# Prayag Production Planning — Replit Build Pack (Master)

This single file contains everything Replit's Agent needs to build the app:
setup, the master prompt, phase prompts, the post‑fetch sanity check, model
tiering, secrets, and the source file‑IDs. Attach `PP_schema.sql`,
`Prayag_PP_Google_Sheets_FileIDs.xlsx`, and (optionally) the Architecture doc
to the first Agent message.

Requirements captured:
- Division dropdown (PTMT / CP) on every screen.
- Buffer **multiplier is a user input** (never hard‑coded); single, or MIN/MAX pair, or per‑category overrides.
- Data fetched by the **Replit Google connector** (read‑only) by file ID.
- After every fetch, data is **sent to Claude for a sanity check** (catch missed/wrong/partial fetches). Claude assesses only — never edits numbers.
- **Logic runs deterministically on Replit** (not Claude); identical numbers regardless of any model.
- **Excel export** of plans; **Claude‑written notes/summary downloadable as PDF**.
- **PostgreSQL** is the single source of truth with **no data duplication** (natural keys + upsert + batch hash).
- **Legacy data imported once** (guarded by an import ledger).
- **Model tiering**: fast model for daily/weekly narrative, deep model for monthly/quarterly/board narrative. **The sanity check always uses the deep model regardless of cadence.**

**System prompt (send as the `system` field):**
```
You are the data sanity checker for a production-planning app. After the Google
Drive connector fetches a batch for a chosen DIVISION (PTMT or CP) and PLAN
MONTH, you receive a NUMBERS-ONLY SUMMARY of the fetch (never the full data).
Judge whether the fetch is COMPLETE and CORRECT, and give concise, de-duplicated,
actionable input. You ASSESS ONLY — never modify, clean, or recompute any data
or numbers, and never run the planning math. Base every conclusion strictly on
the summary; if something can't be determined from it, say so.

== SOURCE MODEL (read before flagging anything) ==
The source workbooks are MULTI-YEAR, FULL-HISTORY files read from a "Combined"
or full-history tab. Therefore:
- Sales and production sources LEGITIMATELY contain rows far outside the plan
  month. A June plan's run-rate window is the three prior calendar months and
  "last month" is the immediately prior month; the engine FILTERS to the window
  downstream. Rows outside the window are EXPECTED, not an error.
- For a June plan, the 3-month sales span legitimately straddles two fiscal-year
  files (e.g. March from Sale 25-26, April–May from Sale 26-27); both files
  being present is correct, not a wrong-file pull.
- `amount != qty * rate` is EXPECTED on many rows because amounts are
  tax-inclusive and/or rounded.
Do NOT raise wrong_month, wrong_file, partial, or unit_mismatch for any of the
above. Only raise wrong_month/wrong_file when the IN-WINDOW data is actually
missing or the file is genuinely the wrong source (see below).

== WHAT IS A REAL PROBLEM ==
Blocker (data must not be used as-is):
- A required source returned 0 rows, OR returned 0 rows INSIDE the plan-month
  window when in-window rows are required (e.g. production for the plan month).
- The file_id used is not among the configured sources for that division/month.
- A column is clearly shifted (values of the wrong kind, e.g. text where qty is
  expected) such that the in-window data is unusable.
Warning (usable, but planner must acknowledge — these change the output):
- No opening-stock snapshot (stock_opening = 0): required quantities assume zero
  stock and will be OVERSTATED. Always raise this when stock is absent.
- Item codes present in sales/orders/production but missing from the items
  master (they will be dropped from the plan).
- A genuine in-window anomaly: impossible negatives, an in-window quantity
  outlier orders of magnitude off history, or in-window row/code count far below
  the previous accepted pull (true partial fetch of the WINDOW, not of history).
Info (note only, no action):
- No pending orders for the plan month (demand excludes pending).
- Expected full-history breadth (out-of-window rows, two-file sales span,
  tax-inclusive amounts) — mention once, collectively, as context, ONLY if you
  reference it; do not enumerate per source.

== DE-DUPLICATION (mandatory) ==
Report each DISTINCT problem EXACTLY ONCE, even if it shows up in several
sources or both per-source and in aggregate. Merge identical issues across
sources into one finding and name the sources in its `source` field
(e.g. "sales, production"). Never emit a per-source finding and a summary
finding for the same problem. Aim for the SMALLEST set of findings that fully
covers the real issues — typically 3–6, not 16. Do not pad.

== EVIDENCE & FIXES ==
For each finding give: the affected source(s); concrete evidence (the numbers
from the summary, and for windowed checks cite the IN-WINDOW figure, not the
whole-file count); and a specific suggested_fix.

== OUTPUT — STRICT JSON ONLY (no prose outside it, no markdown fences) ==
{
  "verdict": "ok" | "warn" | "block",
  "issues": [
    {
      "severity": "info" | "warning" | "blocker",
      "type": "empty|partial|wrong_month|wrong_file|shifted_column|missing_codes|outlier|no_stock|no_pending",
      "source": "<source(s), comma-separated>",
      "message": "<the problem, stated once, plainly>",
      "evidence": "<in-window numbers that prove it>",
      "suggested_fix": "<exact action, or 'none — expected for full-history source'>"
    }
  ],
  "summary": "<one short paragraph: is this fetch safe to plan on, and the few things to fix first>"
}

verdict = "block" if any blocker; else "warn" if any warning; else "ok".
If the in-window data is complete and correct, return verdict "ok" with an empty
issues array even if the files contain large out-of-window history.
```

**Node: assemble the summary, call the deep model, store the result.**
```javascript
const { selectModel, callWithFallback } = require('./models');

// Build a NUMBERS-ONLY summary from the rows just fetched + the last accepted batch.
// NOTE: sources are full-history workbooks, so the IN-WINDOW figures (not the
// whole-file counts) are what the sanity check should judge completeness on.
function buildFetchSummary({ division, planMonth, source, fileId, tab,
                             expectedWindow, expectedFileForMonth, rows, prev,
                             configuredFileIds = [], stockOpeningCount = null,
                             pendingCount = null, orphanCodeCount = null }) {
  const inWin = (d) => d && d >= expectedWindow.from && d <= expectedWindow.to;
  const codes = new Set(rows.map(r => String(r.item_code ?? '').trim()).filter(Boolean));
  const winRows = rows.filter(r => inWin(r.date));
  const winCodes = new Set(winRows.map(r => String(r.item_code ?? '').trim()).filter(Boolean));
  const prevCodes = new Set((prev?.codes) || []);
  const dates = rows.map(r => r.date).filter(Boolean).sort();
  const qty = rows.map(r => Number(r.qty)).filter(n => !Number.isNaN(n));
  const winQty = winRows.map(r => Number(r.qty)).filter(n => !Number.isNaN(n));
  const sum = qty.reduce((a,b)=>a+b,0);
  const winSum = winQty.reduce((a,b)=>a+b,0);
  const outOfWindow = rows.length - winRows.length;
  const missing = [...prevCodes].filter(c => !codes.has(c)).slice(0, 25);
  const negInWindow = winQty.filter(n => n < 0).length;
  const nz = (n,d)=> d ? +(n/d).toFixed(3) : 0;
  return {
    division, plan_month: planMonth, source, file_id: fileId, tab,
    expected_window: expectedWindow,
    expected_file_for_month: expectedFileForMonth,
    configured_file_ids: configuredFileIds,        // so wrong_file is judged correctly
    is_full_history: true,                          // these sources span many years

    // whole-file (context only — do NOT flag on these)
    rows: rows.length, distinct_item_codes: codes.size,
    out_of_window_rows: outOfWindow,
    date_min: dates[0] ?? null, date_max: dates[dates.length-1] ?? null,

    // IN-WINDOW (judge completeness on these)
    in_window_rows: winRows.length,
    in_window_distinct_codes: winCodes.size,
    prev_in_window_rows: prev?.inWindowRows ?? null,
    prev_in_window_distinct: prev?.inWindowDistinct ?? null,
    in_window_neg_qty_rows: negInWindow,
    in_window_qty: { min: winQty.length ? Math.min(...winQty) : null,
                     max: winQty.length ? Math.max(...winQty) : null,
                     mean: Math.round(nz(winSum, winQty.length)), sum: winSum },

    // master / snapshot signals that actually change the plan
    stock_opening_count: stockOpeningCount,         // 0 => no_stock (warning)
    pending_orders_count: pendingCount,             // 0 => no_pending (info)
    orphan_item_codes: orphanCodeCount,             // codes in data not in master

    null_rate: {
      qty: nz(rows.filter(r => r.qty==null||r.qty==='').length, rows.length),
      date: nz(rows.filter(r => !r.date).length, rows.length),
      item_code: nz(rows.filter(r => !r.item_code).length, rows.length),
    },
    numeric_summary: { qty: { min: qty.length ? Math.min(...qty) : null,
      max: qty.length ? Math.max(...qty) : null,
      mean: Math.round(nz(sum, qty.length)), sum } },
    top_missing_codes_vs_prev: missing,
    sample_rows: rows.slice(0, 20),
    deterministic_findings: prev?.deterministicFindings || [],
  };
}

async function runSanityCheck(client, ctx, batchId, db) {
  const summary = buildFetchSummary(ctx);                 // ctx = fetched rows + meta
  const sel = selectModel(ctx.planType, { override: true }); // ALWAYS deep
  const resp = await callWithFallback(client, sel, {
    system: SANITY_SYSTEM_PROMPT,                          // the system prompt above
    messages: [{ role: 'user',
      content: 'Review this fetched batch and return your JSON assessment.\n\n'
               + JSON.stringify(summary, null, 2) }],
    temperature: 0,
  }, (m) => db.markDowngrade(batchId, m));

  const text = resp.content.map(b => b.text || '').join('').trim();
  let result; try { result = JSON.parse(text); }
  catch { result = { verdict: 'warn', issues: [{ severity:'warning', type:'parse',
    message:'Could not parse sanity JSON', evidence:text.slice(0,200),
    suggested_fix:'Re-run the check' }], summary:'Unparseable response.' }; }

  // persist: verdict on the batch, issues as findings (with model/tier provenance)
  await db.setBatchSanity(batchId, result.verdict, result.summary);
  for (const i of (result.issues || [])) {
    await db.addFinding({ import_batch_id: batchId, severity: i.severity, type: i.type,
      message: `${i.source}: ${i.message}`, detail: i,
      source: 'claude_sanity', model: sel.model, tier: sel.tier });
  }
  // gate: block holds the batch; warn needs acknowledgement; ok proceeds
  return result;
}
```

## PART D — The selectModel helper (single source of truth)

```javascript
// models.js — the ONLY place an Anthropic model is chosen
const FAST = process.env.ANTHROPIC_MODEL_FAST || 'claude-sonnet-4-6';
const DEEP = process.env.ANTHROPIC_MODEL_DEEP || 'claude-opus-4-8';
const MAX_FAST = parseInt(process.env.MAX_TOKENS_FAST || '1500', 10);
const MAX_DEEP = parseInt(process.env.MAX_TOKENS_DEEP || '4000', 10);
const DEEP_PERIODS = new Set(['monthly', 'quarterly', 'fiscal_year']);

function selectModel(periodType, { override = null, board = false } = {}) {
  let tier;
  if (override === true) tier = 'deep';          // sanity check passes this
  else if (override === false) tier = 'fast';
  else if (board || DEEP_PERIODS.has((periodType || '').toLowerCase())) tier = 'deep';
  else tier = 'fast';
  return tier === 'deep'
    ? { model: DEEP, maxTokens: MAX_DEEP, tier }
    : { model: FAST, maxTokens: MAX_FAST, tier };
}

// usage — narrative writer (follows cadence):
//   const { model, maxTokens, tier } = selectModel(periodType,
//          { override: deepFlag, board: isBoardReport });
// usage — sanity check (always deep):
//   const sc = selectModel(periodType, { override: true });

module.exports = { selectModel };
```

Fallback wrapper (retry once on FAST if DEEP errors, log the downgrade):
```javascript
async function callWithFallback(client, sel, payload, recordDowngrade) {
  try {
    return await client.messages.create({ model: sel.model, max_tokens: sel.maxTokens, ...payload });
  } catch (e) {
    if (sel.tier === 'deep') {
      recordDowngrade && recordDowngrade(sel.model);              // log it on the artefact
      const fb = { model: process.env.ANTHROPIC_MODEL_FAST || 'claude-sonnet-4-6',
                   max_tokens: parseInt(process.env.MAX_TOKENS_FAST || '1500', 10) };
      return await client.messages.create({ ...fb, ...payload });
    }
    throw e;
  }
}
```

## PART F — Acceptance criteria

**Data & engine**
- Re-pulling the same month updates rows in place (no duplicates); an identical batch is skipped as 'no change'.
- The multiplier is taken from the run (never hard-coded); the plan_run stores the multiplier(s) used and is reproducible.
- Legacy import refuses to run a scope twice.

**Sanity check**
- An empty/partial pull, wrong-month, wrong-file, or shifted column is caught and HOLDS the batch with a named Re-fetch action.
- The sanity-check Claude call runs on the **deep** model even for a daily/weekly pull (recorded `tier='deep'`), while that run's report narrative may be fast.
- Claude's findings are stored and shown; no data values are altered by the check.

**Tiering**
- Daily/weekly narrative uses `ANTHROPIC_MODEL_FAST`; monthly/quarterly/board narrative uses `ANTHROPIC_MODEL_DEEP` — verifiable from recorded `model`/`tier`.
- "Deep analysis" override forces deep on a fast period and vice-versa (narrative only).
- Changing the Secrets swaps models with no code change.
- Identical input data yields identical numeric tables on both tiers (only prose differs).
- If the deep model errors, the run completes on the fast model and the downgrade is logged.
