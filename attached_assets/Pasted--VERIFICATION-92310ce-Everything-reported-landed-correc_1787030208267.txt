## ❌ The check name shows the wrong operands, and only fails visibly when it matters

`:1164`:

```typescript
name: `ExportTotals · |item-round orig (${itemOrigSum}) − stored real orig (${storedOrig})| = ${origDivergence} pcs ≤ 500`,
```

`origDivergence` is computed at `:1146` from **`detailOrigHeader`**, not `itemOrigSum`:

```typescript
const origDivergence = Math.abs(detailOrigHeader - storedOrig);
```

When the parse succeeds these agree, so the name reads fine. **When the parse fails — the case checks 7–8 exist to catch — `detailOrigHeader` is `-1` and the name becomes self-contradictory:**

```
ExportTotals · |item-round orig (617750) − stored real orig (617711)| = 617712 pcs ≤ 500   FAIL
```

Two numbers 39 apart, reported as a divergence of 617,712. Anyone reading that red line concludes the check is broken, not the export — which is the opposite of what a failure message is for, and it fires precisely when someone is under pressure to interpret it quickly.

The comment at `:1160–1161` has the same slip: *"After the fix, detailOrigHeader = itemOrigSum … so origDivergence = |itemOrigSum − storedOrig|."* True only on the success path; the sentinel exists specifically so that equality does **not** hold on failure.

**Fix:** interpolate the actual operand.

```typescript
name: `ExportTotals · |detail orig header (${detailOrigHeader}) − stored real orig (${storedOrig})| = ${origDivergence} pcs ≤ 500`,
```

Same for `:1170` / `planDivergence` / `detailPlanHeader`. Then a parse failure reads `|-1 − 617711| = 617712 pcs ≤ 500 FAIL`, which points straight at the unparsed header.
