## ❌ A2 — the fix I specified in B2 is not implementable as written

`workingDaysRemaining` is **forward-looking** from the as-of date. At run time, no Sunday in that window has been worked yet — you cannot observe the future.

Your A2 figures add Aug 9 to a window starting Aug 8, which only works because you are recomputing on 20 August, eleven days after the fact. A corrective actually run on 7 August could not have known Aug 9 would be worked. So "corrected = 21" is a retrospective number, not the output of an implementable fix. **My B2 instruction was wrong.** Do not implement it.

The underlying defect is still real, but it is a different one: **Cap/Day and remaining days come from different populations.**

- Cap/Day is derived from `dailyByCat`, which includes Sundays — so it is the plant's capability per *production day*.
- Remaining is calendar non-Sundays — *working days*.

`feasible = capability-per-production-day × working-days` is neither a true capacity estimate nor a conservative one. Two coherent ways to fix it; pick one, don't mix:

| Option | Cap/Day basis | Remaining basis | Meaning |
|---|---|---|---|
| **A — consistent & conservative** | non-Sunday days only | calendar non-Sundays | "what we can do on normal working days" |
| **B — full capability** | all production days (unchanged) | calendar non-Sundays + *expected* Sundays | "what we can do including likely Sunday working" |

Option B needs a policy input — expected Sundays could be `observed Sunday-working rate × remaining Sundays` (PTMT: 3 of 4 in June → 0.75) or a configured value. It cannot be observed.

**I'd suggest A as the default**, with B available where the team says Sunday working is planned rather than exceptional. A is a one-line change to `computeCapByCategory`'s input filter and makes both sides calendar-based. But this is a business call about whether Sunday working is normal capacity or overtime — the same question you already answered for pace metrics, now for feasibility.

Worth noting the direction: under A, Cap/Day **falls** (Sunday days leave the p90 sample), so feasible falls and shortfall **rises** — the opposite of the A2 table. That is the honest conservative answer, and it should not be a surprise when it lands.

## ❌ A5 — `commitSha` will never work, and I can see why

`buildInfo.ts:9–13`:

```typescript
return execSync("git rev-parse HEAD", { encoding: "utf-8", stdio: ["pipe","pipe","pipe"] }).trim();
```

It shells out to **git at runtime**. The deployed container runs `node artifacts/api-server/dist/index.cjs` from a build artefact with no `.git` directory — so `execSync` throws and the catch returns `"(unknown)"`. Exactly as the comment predicts.

This is not a publish failure. **It cannot work in production by construction**, and the metric that has been used to judge four deployments has never been capable of reporting.

Also: dev reports `4ae1358`, which does **not** exist on `origin/main`. So dev is running yet another unpushed commit.

**Fix:** inject the SHA at build time. In `esbuild.build.mjs`:

```javascript
define: { "process.env.GIT_COMMIT": JSON.stringify(process.env.GIT_COMMIT ?? execSync("git rev-parse HEAD").toString().trim()) }
```

and have `buildInfo.ts` read `process.env.GIT_COMMIT` first, falling back to the runtime `git` call for dev. Then the value is baked into the bundle and survives the container.

This should go **before** B1 and B2 — until it works, there is no way to confirm what production is running, which is the question that has come up in four consecutive rounds.
