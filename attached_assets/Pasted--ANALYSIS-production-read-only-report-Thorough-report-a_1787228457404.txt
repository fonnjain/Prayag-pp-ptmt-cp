## ⚠ The important finding: there are two snapshot tables, and the wrong one is empty

> *"The deployed lazy-capture path targets `plant_monitoring_snapshots`. It is separate from the currently empty `plant_month_snapshots` table."*

Confirmed in the schema. Two distinct tables exist:

| Table | Purpose | Key | Segment-aware? |
|---|---|---|---|
| `plant_monitoring_snapshots` | what lazy capture actually writes | `month` (PK) | **no** |
| `plant_month_snapshots` | what the freeze design specifies | `(month, segment)` unique | yes |

The freeze work — migration 024, `closed_at` / `captured_at` / `captured_commit_sha` / `backfilled`, and migration 027's `plan_status` — all landed on `plant_month_snapshots`. **The code that actually runs on a closed-month read writes to `plant_monitoring_snapshots` instead**, which has none of those columns and is keyed on `month` alone with **no segment column**.

Three consequences:

1. **The provenance fields are unreachable.** `captured_commit_sha`, `backfilled`, `plan_status`, `plan_status_reason`, `plan_evidence_json` sit on a table nothing writes. Every guarantee we built — knowing when a snapshot was taken, by which build, whether it was backfilled, whether its plan was rejected — is inert.
2. **`plant_monitoring_snapshots` cannot hold both segments.** `month` is the primary key. PTMT and Plumbing for 2026-06 would collide; one overwrites the other. The June seed in dev wrote two rows to `plant_month_snapshots`, which supports that — but the deployed path can't.
3. **Production has never captured anything** despite the scheduler running hourly during IST work hours since deployment. Either the lazy path isn't firing, or it is firing and writing rows the report didn't query. Worth establishing which, because "the table is empty" and "capture never ran" are different findings.

This is the same class as the wrong-workbook archive from Prompt 1 — verification against the object the code doesn't use. It's worth asking whether `plant_month_snapshots` was ever wired up, or whether the whole freeze feature has been building alongside a live path that ignores it.

## What I'd ask next

Read-only again, because the two-table question changes what "seed production" even means:

> **1. Query `plant_monitoring_snapshots` in production** — all rows, with `month`, `plan_run_id`, `captured_at`, and the produced total from `bundle_json`. The previous report queried the wrong table. If rows exist there, they were captured by the deployed code and need checking against the true totals for the Sunday drop.
>
> **2. Which table does a closed-month read actually consult?** Trace `plant-monitoring.ts` for a closed month end to end and state whether `plant_month_snapshots` is read or written on **any** live path. If it isn't, the freeze feature is not deployed regardless of what the migrations say.
>
> **3. If both tables are in use, what is the intended relationship?** `plant_monitoring_snapshots` is keyed on `month` alone and cannot hold two segments — so either it is PTMT-only by design, or Plumbing's snapshots are colliding with PTMT's.
>
> **4. Was the June dev seed written to `plant_month_snapshots`?** If so it is in the table nothing reads, and "June is frozen in dev" may not be true in the sense that matters.
>
> Then, before seeding production: publish `bb6b6f5` so migration 027's columns exist, and confirm `/healthz commitSha` matches.

**Do not seed production June until the two-table question is settled.** Writing to the table nothing reads would look like success and change nothing — and writing to the one that is read would drop a segment, since it cannot hold both.
