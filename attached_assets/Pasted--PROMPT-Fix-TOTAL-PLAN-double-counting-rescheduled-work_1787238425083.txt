# PROMPT — Fix `TOTAL PLAN` double-counting rescheduled work

`TOTAL PLAN` on the Ops Overview and in the Plan-vs-Actual report counts the same physical work once per plan version. PTMT August reads **11.9L** against a monthly plan of roughly **6.2L**.

**Read-only Part A first. Do not change code until Part A is reported.**

---

## The defect

**Day attribution is already correct** — `buildVersionAwarePlanMap` (`plan-vs-actual-engine.ts:305–325`) picks one governing version per calendar day and weights by `count / totalDays`, so a week straddling a plan change splits proportionally. That half is right and must be preserved.

**The quantities are not.** Two behaviours combine:

**1.** A plan run puts an item's **entire monthly quantity into one week** — `plant-plan-timeline.ts:231–234`:

```javascript
w1: week === 1 ? item.productionPlan : 0,
w2: week === 2 ? item.productionPlan : 0,
```

**2.** A corrective puts that item's **`remainingToProduce` into a later week** — `corrective-engine.ts:756–759`:

```javascript
item.w1Rev = finalWeek === 1 ? item.remainingToProduce : 0;
item.w2Rev = finalWeek === 2 ? item.remainingToProduce : 0;
```

`remainingToProduce = planRev − producedToDate` — the **same pieces**, rescheduled.

### Worked example

Item X, monthly plan **1,000 pcs**, assigned Week 1 by plan run #20. Nothing produced by 8 August. Corrective #10 moves the outstanding 1,000 to Week 3.

| Week | Governing version | Counted |
|---|---|--:|
| W1 (1–7 Aug) | plan run #20 | 1,000 |
| W3 (15–21 Aug) | corrective #10 | 1,000 |
| | **TOTAL PLAN** | **2,000** |

Planned 1,000, counted 2,000. Every unproduced item is counted once by the version that scheduled it and again by each corrective that pushes it forward.

### The rule this must satisfy

> A recompute plans only from its effective date to month end. The earlier plan counts only up to that date. Rescheduled work **replaces** the earlier version's unfulfilled portion — it does not add to it.

## PART B — The fix

### Use a daily rate, consistent with what monitoring already does

`plant-engine.ts:256–262` already computes required-per-day exactly this way:

```javascript
const version = versionForDate(versionTimeline, date);
const total = activeTargets.reduce((sum, t) => sum + t.maxPcs, 0);
dailyRequiredByDate.set(date, total / workingDays);
```

Apply the same shape to the plan total:

```
TOTAL PLAN = Σ over working days d in the month
               ( version_governing(d).monthTotal ÷ version_governing(d).workingDays )
```

One version per day, one quantity per day — **double-counting becomes arithmetically impossible**. It also makes Plan-vs-Actual and the monitoring dashboard agree on what "plan" means, which they currently don't.

`workingDays` must come from `resolveWorkingDays(month, configured)` so worked Sundays are included, consistent with the rest of the app.

### Keep the weekly buckets, but relabel them

W1–W4 stay for the weekly-release view. **Do not present their sum as `TOTAL PLAN`** — that sum is the double-counted figure. Label the weekly block as the release schedule, and take the headline total from the daily-rate calculation.

If you believe the weekly buckets must reconcile to the total instead, say so before implementing — that is the alternative design (subtract, before summing a corrective's `wXRev`, the portion of that item already counted in earlier-governed weeks) and it needs exact bookkeeping. **Do not pick between these silently.**

### Add the invariant that would have caught this

The only plan check today is `catPlanSum === kpis.totalPlan` (`:965`) — internal consistency, which passes happily while the total is double the real plan. Add:

```
TOTAL PLAN ≤ (largest single version's month total) + (new demand added mid-month)
```

Anything beyond that bound is double-counted rescheduling.

### Tests

1. **The worked example above** — one item, 1,000 planned in W1, rescheduled to W3 by a corrective. `TOTAL PLAN` must be **1,000**, not 2,000. This is the regression test; write it first.
2. Single version, no corrective → `TOTAL PLAN` equals that version's month total exactly.
3. Two versions, boundary mid-week → the day-share split is preserved (do not regress the correct half).
4. A corrective that adds genuinely **new** demand → the total rises by the new demand only.
5. The new invariant fails when fed a deliberately double-counted timeline.
