## The 28-piece gap is expected, and it is evidence the fix works

The 489,790 figure came from a screenshot of the **live dashboard on 19 August**, taken before versioning landed. At that point W1's release was computed by `buildPlanItems(month)` — a rebuild from whatever the uploads contained at that moment. Run #20's stored snapshot says W1 = **489,818**.

So the two numbers are not two readings of the same thing. One is a frozen snapshot of run #20; the other is a live rebuild two days later, drifting as uploads changed underneath it. **A 28-piece difference is precisely the drift the freeze was built to eliminate.** I'd record it that way in the memory note rather than as an open discrepancy.

## ⚠ Run #18's W1 of 684,492 looks like the whole month, not week 1

`684,492` is the **month total** for plan run #18 — that figure appears throughout this session's notes as PTMT August's month grand total, never as a weekly release.

`plant-plan-timeline.ts:209–234` explains how that can happen:

```typescript
const allocationRows = linkedCorrective
  ? await db.select().from(correctivePlanItemsTable).where(…)
  : [];
const allocationByKey = new Map(allocationRows.map(…));
…
const week = allocationByKey.get(`${item.itemCode}|${item.colour}|${item.category}`) ?? 0;
w1: week === 1 ? item.productionPlan : 0,
```

The weekly split for a `run` version comes **only** from a linked corrective run's item allocations. When a plan run has no linked corrective — which `c24eaab` just made survivable rather than a crash — `allocationRows` is empty and every item falls to `week = 0`, so **w1, w2, w3 and w4 are all zero** and the entire month's quantity has no week.

That doesn't produce 684,492 in W1 by itself, so one of two things is true, and it's worth knowing which:

1. Run #18 **does** have a linked corrective whose allocations put everything in week 1 — plausible if the corrective ran in W1, but then the shape is real and W1-heavy by construction; or
2. Something downstream folds an all-zero weekly split back into W1 as a fallback, in which case every legacy run without a corrective will report its full month total as W1 — exactly the W1-489,790-then-W2-47,194 shape in the original screenshot.

Case 2 would mean the versioning work faithfully preserved a pre-existing weekly-split defect rather than fixing it, and the dashboard would still be wrong for the reason you were originally chasing.

**Please check:** for run #18, does a linked `corrective_plan_runs` row exist, and do its `correctivePlanItems` allocate to week 1? And what are w2/w3/w4 in run #18's stored version snapshot — if they're all zero while w1 is 684,492, that is case 2.

The plan runs themselves already carry a weekly split. `plan_run_results` has the banding available, and `buildPlanItems` computes `w1..w4` via `annotateWeeklyRelease` (`calc.ts:118–137`) using the category cover bands. Sourcing the run version's weekly split from there, rather than from a linked corrective that may not exist, would make it correct independent of whether a corrective was ever run.
