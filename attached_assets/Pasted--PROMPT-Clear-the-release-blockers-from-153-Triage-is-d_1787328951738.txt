# 1 — `monitoring.ts:389` serves PTMT data under another segment's label ⬤ highest priority

## The defect

```typescript
const segment = normalizePlantSegment(req.query.segment);   // :389 — returns null for unknown

if (segment === "Plumbing") {                                // :393
  …
}
// ← null falls through here into the PTMT branch
```

`normalizePlantSegment` returns `null` for an unrecognised value. `null !== "Plumbing"`, so execution continues into the PTMT path and **returns PTMT numbers**. No error, no log, HTTP 200.

You reproduced this in production. It is the worst kind of defect in this system: every other blocker on the list announces itself with a 500; this one produces a plausible wrong answer under a label that says something else.

Your triage confirmed `:697`, `:724`, `reports.ts:191` and `:214` already handle `null` correctly — so this is one site, not five.

## Fix

Reject before branching:

```typescript
const segment = normalizePlantSegment(req.query.segment);
if (segment === null) {
  res.status(400).json({
    error: "Unrecognised segment",
    value: String(req.query.segment),
    recognised: PLANT_SEGMENTS,
  });
  return;
}
```

Name the offending value and list what is accepted. A bare 400 leaves the caller guessing.

## Also fix the root cause, not just this site

`plant-segments.ts:28–42` hardcodes both functions against string literals rather than the registry:

```typescript
export function isPlantSegment(value: unknown): value is PlantSegment {
  return value === "PTMT" || value === "Plumbing";
}
```

Adding CP to `PLANT_SEGMENT_PROFILES` would widen the type via `as const` while these two keep rejecting it. Derive them:

```typescript
const BY_LOWER: ReadonlyMap<string, PlantSegment> =
  new Map(PLANT_SEGMENTS.map((s) => [s.toLowerCase(), s]));

export function isPlantSegment(value: unknown): value is PlantSegment {
  return typeof value === "string" && BY_LOWER.has(value.trim().toLowerCase());
}

export function normalizePlantSegment(
  value: unknown,
  fallback: PlantSegment | null = "PTMT",
): PlantSegment | null {
  if (value === undefined || value === null || value === "") return fallback;
  return BY_LOWER.get(String(value).trim().toLowerCase()) ?? null;
}
```

Update `plant-cache.test.ts:93` — it asserts `normalizePlantSegment("CP") === null`, correct today and wrong the moment CP is registered. Use a value that will never be registered, e.g. `"NOT_A_SEGMENT"`.

## Tests

- Every value in `PLANT_SEGMENTS` round-trips in lower, upper and title case
- `GET /api/monitoring/dashboard?segment=NOT_A_SEGMENT&month=2026-08` → **400**, not 200
- **The regression test that matters:** an unrecognised segment must never return a payload whose numbers match PTMT's. Assert the status, not just the shape

# 2 — Plumbing parser skips `* PIPE` tabs ⬤ unblocks four endpoints

## The defect

The July Plumbing workbook exposes `CPVC PIPE`, `UPVC PIPE`, `SWR PIPE`, `AGRI PIPE`. The parser skips them, produces no average-sale rows, and raises `PlanningInputError` — which surfaces as a generic **HTTP 500** across three validation endpoints and the Plumbing monitoring dashboard.

## Fix, in two halves — do both

**2a. Teach the parser the tab names.** Report first: list every tab in the July workbook, which the parser currently matches, and which it skips. Then widen the matching. Prefer a normalised comparison (case, spacing, separators) over adding four literals, since the same drift will recur next month.

**2b. Make an unreadable tab a named error, not a 500.** This is the part that matters more than the parse fix.

Right now the parser reading nothing produces the same response as the server crashing. Return a **422** identifying what could not be read:

```json
{
  "error": "PLUMBING_INPUT_UNREADABLE",
  "month": "2026-07",
  "workbookId": "1wlB4Y4…",
  "skippedTabs": ["CPVC PIPE", "UPVC PIPE", "SWR PIPE", "AGRI PIPE"],
  "detail": "No average-sale rows produced — these tabs were not recognised"
}
```

**This is the silent-input-failure pattern one layer down.** The parser found tabs it did not understand and responded by producing nothing rather than saying what it could not read. Unrecognised headers joining as zero, `?? 27` for working days, `normalizePlantSegment` returning null — same shape each time. Naming the skipped tabs turns a 500 into a five-minute diagnosis.

## Tests

- A workbook containing `* PIPE` tabs parses and yields average-sale rows
- A workbook with a genuinely unknown tab returns **422 naming that tab**, not 500
- The three validation endpoints and the Plumbing monitoring dashboard return 200 for July after the fix

# 4 — PTMT plan PDF 500 after ~41.5 s

## Likely cause — check before fixing

41.5 seconds is close to a timeout boundary, not a code fault. Plumbing succeeds at 1,120 items; PTMT has **3,636**.

`browser.ts` sets `protocolTimeout: 120_000` but **never sets `timeout`**, which governs navigation and page operations and defaults to **30 s**. And `pdf-export.ts:94–95` sets neither:

```typescript
await page.setContent(html, { waitUntil: "networkidle0" });   // no timeout
const pdfUint8 = await page.pdf({ … });                       // no timeout
```

I flagged the missing `timeout` when `browser.ts` was introduced; it was not added.

**Report the actual error text before changing anything.** If it names a timeout, fix as below. If it is something else, stop and report — do not raise timeouts to mask a different fault.

## Fix, if it is a timeout

```typescript
// browser.ts
timeout: 120_000,          // alongside protocolTimeout

// pdf-export.ts
await page.setContent(html, { waitUntil: "networkidle0", timeout: 120_000 });
const pdfUint8 = await page.pdf({ …, timeout: 120_000 });
```

Also report how long PTMT takes once it succeeds. If it is 60 s+, raising the limit is a workaround and the render itself needs attention — 3,636 rows through `networkidle0` is a lot of DOM.
